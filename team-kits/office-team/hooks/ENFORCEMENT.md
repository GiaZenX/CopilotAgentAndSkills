# Enforcement reference — what each mechanism refuses (office-team)

The table your constitution names in §2 ("Guardrails + hard backstops") and no longer carries. It
lives here because the constitution loads at every session start and at every subagent spawn, while
this is REFERENCE: it is what you need at the moment a gate has refused a call, not before. Nothing
loads it for you — `AGENTS.md` does not import it, it is no preloaded skill, and the session-start
hook does not inject it. Every refusal a gate writes prints the path of this file, so the moment you
need the table is the moment you are handed its location.

It ships inside the hashed enforcement bundle (`.claude/hooks/`), which is what makes it as
tamper-evident as the mechanisms it describes: `guard_harness_selfmod` refuses an Edit/Write under
`.claude/hooks/`, `gate_write_scope` refuses a write-capable shell pipeline that names the layer,
and any change to this file moves the bundle hash `hook_trust` compares.

Reading a row: the left cell names the mechanism, the right cell says what it refuses and — where
the rule has one — the condition under which it does not refuse at all.

One rule has to travel WITH its rows rather than be looked up, because two rows below presuppose it
and a reader who arrives here after a refusal has only this file in front of them: **ledger edits
are allowed and ALWAYS validation-required** (user decision V2 I.3/1 — append-only is gone). Its
home is §2 of your constitution; `gate_ledger_valid` and `guard_fs_tripwire` below are what enforces
it, not a stricter version of it.

## 1. What each mechanism refuses

| Hook | Blocks / does |
|---|---|
| `guard_agent_spawn` | Claude blocks a spawn issued FROM a subagent at all (only the session instance delegates — the payload names its caller only inside a subagent, `_compat.calling_subagent`), plus generic/unnamed spawns, a second manager, missing explicit `run_in_background`, and incomplete work orders; Codex cannot veto `SubagentStart`, so exact-role policy + specialist work-order validation cover that gap. Plus (V2, spec II.4) `gate_dispatch`: no spawn without a valid `HARNESS_DISPATCH` header + live lease — missing task, wrong role, stale root revision, unproven or invalidated approval, open dependency, spent lease, missing `design_ref` for a UI task with a confirmed design; it binds the child's `agent_id` to its task. A spawn that does not start returns the task to READY: at once on `PostToolUseFailure`, and otherwise by its bind window closing with no child (reconciled at the next spawn attempt, at `Stop`, and by `python scripts/harness.py sweep-leases`). The second half is not redundancy — measured 2026-08-02 in twelve real sessions, a spawn the permission layer refuses fires NO hook event at all, and `PermissionDenied`, which used to carry the rollback, fired in none of them. The gate spends the lease only in one chained process behind every other PreToolUse spawn gate, because a sibling's exit 2 does not stop it |
| `gate_subagent_output` | a specialist stopping without its output contract (`summary:` at minimum) — prose-only endings produced work built on air |
| `gate_proc_approved` | a specialist spawn whose work order names no `PROC-nnnn`, names one the user never approved, or names one whose content no longer matches the `approved_hash` the mint stamped on it. It reads `procedures/active/PROC-*.yaml`, and an EMPTY store is a refusal too (spec II.4) — the installer's bootstrap window is the only exception |
| `gate_ledger_valid` | after ANY edit to `ledger/*.csv`: full-file validation (schema, dates, year, net×(1+vat)≈gross, duplicate invoices, `reverses` targets); on failure the ledger is marked INVALID and push/merge/reports/dispatch are refused until fixed |
| `gate_filing` + `guard_no_adhoc` + `guard_pm_scope` | a file landing under `archive/` in a place no `filing_plan.yaml` rule covers — via a shell move OR a direct write; and every filing while the plan still lists no rules. Plus `gate_write_scope` (V2, II.4 gate 3): ANY tool write into `project_memory/**` (one writer, the kernel; an agent gets only `staging/<its task-id or root-id>/`), a bound specialist writing outside its `allowed_scope`, an UNBOUND subagent writing anything, and from a shell: the harness subcommands that ORDER work — creating a task, or leasing one for a spawn; `gate_write_scope._ORDERING_COMMANDS` is the set, and a test derives it from the kernel CLI's own routes — when the caller is a subagent — its own `submit-result`/`evidence` stay open — plus naming `project_memory` or the enforcement layer in anything but a read-only command (so copying the hooks elsewhere is refused, reading them is not). Plus `guard_no_adhoc`: the ad-hoc status/summary/result files item 1 forbids, on the `Write` tool, for YOU and every specialist. Plus `guard_pm_scope`, for YOU ALONE (it skips every call carrying an `agent_id`, i.e. every subagent): a write of PRODUCTION CODE — a file in a programming LANGUAGE outside your own areas (`project_memory/**`, `.claude/**`, `plans/**`, `docs/**`, root config/markdown). The language decides, not the directory: measured rc 2 for `tools/sales_extract.py` AND `dashboards/build.js` — both the office-developer's (§2.1) and both to delegate — and for `scripts/euer_report.py` — the renderer item 4 says produces the reports, so a hand-written report is the wrong artifact before it is the wrong writer. `dashboards/sales.html` and `reports/euer_*.md` are not a programming language and pass. Both of those act on the Edit/Write TOOL call, so a write performed from a SHELL passes them |
| `guard_fs_tripwire` | a shell command that DELETES something whose resolved position is under `inbox/` or `archive/`, and one that MOVES a document whose resolved source is under `archive/` to a destination outside it. Both halves are about where the operands land, not about the word `archive` appearing in them: a move that stays inside the archive is reorganisation and passes however it is spelled, and a `cd` into the archive followed by a relative move or delete does not hide either one. A move INTO the archive is filing and is `gate_filing`'s question, not this guard's. What it does not see: a removal performed inside another program, and an operand the shell rewrites before use (a variable, a glob, `~`) — uncertainty leaves the command alone. Plus `gate_push_token` (R1): `git push` needs a user approval minted through the approval flow and bound to remote+branch+HEAD — a new commit invalidates it. That token cannot cover a FORCE push, because it binds the commit and not the remote's history, so this gate refuses one outright — on `_compat.names_force_push`, so `--force`, `-f`, `--force-with-lease` and a `+refspec` are one rule and not four (a `--dry-run` does not excuse it, and it is refused before the approval is even looked up). This kit installs no second git gate, so that refusal is the whole rule here. Plus `gate_shell_hygiene` (R10/R11): destructive `docker` on a FOREIGN compose project or any `prune`; merge/rebase/pull/`reset --hard`/branch-switch on a dirty tree (`git add`/`stash`/`checkout -b` stay open) |
| `guard_question_context` | user questions referencing INVISIBLE context ("wie oben zusammengefasst" — thinking/tool calls are unseen); questions must be self-contained or preceded by visible text. Plus `gate_approval` (V2, spec II.2): a question marked `[APR-REQ:<id>]` must match the kernel-generated approval question EXACTLY (text, header, every option) or it is blocked; only the verbatim `Freigeben [code]` label mints the approval |
| `guard_yaml_valid` | invalid `project_memory/*.yaml` at write time — well-formedness only (parse errors, duplicate keys); what an item must CONTAIN is its TYPE's field contract, which the state validator answers (`python scripts/harness.py validate`) Plus `guard_memory_budget` (V2, spec II.5): a MEMORY.md index over 40 lines / 8 KB, a craft topic over 100 lines / 8 KB, any OTHER file in agent-memory over 8 KB, a 21st topic for one role, or ANY project item id in a role's memory — memory holds craft, never project status (put an id in `backticks` to quote it) |
| `guard_scratchpad_ref` | repo files referencing ephemeral session-scratchpad paths |
| `guard_harness_selfmod` | Claude hard-blocks edits to `.claude` enforcement; Codex blocks through trusted `PreToolUse` plus read-only permission-profile paths (the Office kit has no CI backstop) |
| `notify_agent_events` / `session_status` / `kit_trust_state` | (never block) lifecycle audit log / session-start briefing incl. inbox count, due reports, stale compliance entries, kit-update + model/effort nags / records which hook bundle this project trusts in `.claude/kit_state.json` (`restart_required` -> `active`; `hooks_trust_required` when the bundle changed) -- doctor measures `hook_trust` against it, and `gate_dispatch` REFUSES every specialist spawn while the installed bundle is not the recorded one (it compares the hashes itself, so a bundle changed mid-session counts too; `restart_required` is not that case and delegation stays open there). ANY difference counts, a stray `.pyc` cached into `.claude/kernel/__pycache__` included -- measured: one such file stops every delegation, and removing that `__pycache__` directory restores the recorded hash on its own (bytecode is not part of what the scaffold installs). A project carrying NO `kit_state.json` has nothing to compare and is not stopped. Touching the record is refused on every route that NAMES the layer -- Edit/Write by `guard_harness_selfmod`, and a shell pipeline by `gate_write_scope` (measured for `rm`, `rm -f`, `del`, `Remove-Item`, an inline `os.remove` and `cd .claude && rm`). What still gets through is the complement: a command line that names it NOWHERE -- a glob, `find`, `git clean -xfd`, or a script the agent runs. That route can not only DELETE the record but REWRITE it with the hash of an already-tampered bundle, and a re-blessed bundle is then indistinguishable from an untouched one (measured: one byte appended to a hook -> spawn refused; the same command line re-blessing the record -> refusal gone). `kit_state.json` cannot live inside the hashed set, because it holds that set's hash -- so this is a limit of the record, and the reason `hook_trust` is a doctor CAPABILITY and not a proof |
