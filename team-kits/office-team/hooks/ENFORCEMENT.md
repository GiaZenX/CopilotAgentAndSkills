# Enforcement reference — what each mechanism refuses (office-team)

The table your constitution names in §2 ("Guardrails + hard backstops") and no longer carries. It
lives here because the constitution loads at every session start and at every subagent spawn, while
this is REFERENCE: it is what you need at the moment a gate has refused a call, not before. Nothing
loads it for you — `AGENTS.md` does not import it, it is no preloaded skill, and the session-start
hook does not inject it. Every refusal a gate writes prints the path of this file, so the moment you
need the table is the moment you are handed its location.

It ships inside the hashed enforcement bundle (`.claude/hooks/`), which is what makes it as
tamper-evident as the mechanisms it describes: `guard_harness_selfmod` refuses an Edit/Write under
`.claude/hooks/`, `gate_write_scope` refuses a write-capable shell pipeline that names the layer,
and any change to this file moves the bundle hash `hook_trust` compares.

Reading a row: the left cell names the mechanism, the right cell says what it refuses and — where
the rule has one — the condition under which it does not refuse at all.

One rule has to travel WITH its rows rather than be looked up, because two rows below presuppose it
and a reader who arrives here after a refusal has only this file in front of them: **ledger edits
are allowed and ALWAYS validation-required** (user decision V2 I.3/1 — append-only is gone). Its
home is §2 of your constitution; `gate_ledger_valid` and `guard_fs_tripwire` below are what enforces
it, not a stricter version of it.

## 1. What each mechanism refuses

| Hook | Blocks / does |
|---|---|
| `guard_agent_spawn` | Claude blocks a spawn issued FROM a subagent at all (only the session instance delegates — the payload names its caller only inside a subagent, `_compat.calling_subagent`), plus generic/unnamed spawns, a second manager, missing explicit `run_in_background`, and incomplete work orders; Codex cannot veto `SubagentStart`, so exact-role policy + specialist work-order validation cover that gap. Plus (V2, spec II.4) `gate_dispatch`: no spawn without a valid `HARNESS_DISPATCH` header + live lease — missing task, wrong role, stale root revision, unproven or invalidated approval, open dependency, spent lease, missing `design_ref` for a UI task with a confirmed design; it binds the child's `agent_id` to its task. A spawn that does not start returns the task to READY: at once on `PostToolUseFailure`, and otherwise by its bind window closing with no child (reconciled at the next spawn attempt, at `Stop`, and by `python scripts/harness.py sweep-leases`). The second half is not redundancy — measured 2026-08-02 in twelve real sessions, a spawn the permission layer refuses fires NO hook event at all, and `PermissionDenied`, which used to carry the rollback, fired in none of them. The gate spends the lease only in one chained process behind every other PreToolUse spawn gate, because a sibling's exit 2 does not stop it. AND, at the end of the LEAD's turn, it names every dispatch whose own RECORDS say no child is on it -- the child's stop was recorded at `SubagentStop`, or the dispatch window ran out with no child ever bound to it -- with what that run left in staging and the no-progress status the task's own automaton offers. A BOUND child that outlived its lease is deliberately NOT among them: a running child may outlive its lease (the lifecycle says so at `dispatch.LEASE_MINTED_STATUS`), and reporting one cost a measured false alarm whose remedy would have ended a live run. That one is a REFUSAL: on `Stop`, exit 2 does not end the turn and hands the assistant this stderr, so the finding reaches the lead instead of another "it is running" -- that is the provider's documented exit-code contract for the event, and what a real session does with it is measured in the live run and not by this repo, which has only measured that `Stop` FIRES (BUG-0058, pilot 4 P4-2, where nine consecutive waiting turns passed with a dead child and an empty staging directory). It refuses AT MOST once per finding and not at all on a stop the provider marks as one a hook already blocked, because a refused stop is answered by continuing; a second silence is therefore NOT caught, and how long that provider mark stays set is unmeasured -- a sticky one would make this silent rather than repetitive, and the task is never moved -- what to do about the finding stays the lead's. The recorder runs LAST in the `SubagentStop` chain: the gate ahead of it can turn that stop into a continuation, and a child told to keep working has not ended |
| `gate_subagent_output` | a specialist stopping without its output contract (`summary:` at minimum) — prose-only endings produced work built on air. **It does NOT refuse a SECOND time**: once a stop hook has blocked this cycle the provider sets `stop_hook_active`, and blocking again would loop the subagent forever — so the retry is let through with whatever it carries, and only the audit says which of the two happened (`retry_delivered` or `gave_up`, BUG-0049). A second consecutive violation is therefore unblocked. |
| `gate_proc_approved` | a specialist spawn whose work order names no `PROC-nnnn`, names one the user never approved, or names one whose content no longer matches the `approved_hash` the mint stamped on it. | `gate_ledger_valid` | after ANY edit to `ledger/*.csv`: full-file validation (schema, dates, year, net×(1+vat)≈gross, duplicate invoices, `reverses` targets); on failure the ledger is marked INVALID and push/merge/reports/dispatch are refused until fixed |
| `gate_filing` + `guard_no_adhoc` + `guard_pm_scope` | a file landing under `archive/` in a place no `filing_plan.yaml` rule covers — via a shell move OR a direct write; and every filing while the plan still lists no rules. **The CONTENT review in front of it is still procedure and not a mechanism** (constitution §2.5, FR-0049): the clerk's per-document proposal and the filing-reviewer's `accept`/`object`/`partial` verdict live in `staging/<TSK-ID>/`, and NOTHING validates either against its shape — `guard_yaml_valid` parses both for well-formedness like any other state YAML and that is the whole of what reads them, so an unreviewed proposal reaches this gate exactly like any other move and what THIS gate refuses is unchanged. **What is now a mechanism is the CLASSIFICATION agreement**, and it is the row below (`gate_second_reading` + `record_filing_reading`, FR-0035): a document entering a plan-covered archive path is refused unless two records attested to two DIFFERENT runs put it at the same path under the same name. What DID change is the way out of a refusal: a class the plan does not cover is no longer a dead end, because `python scripts/harness.py add-filing-rule` appends one rule the user minted a `filing_rule` approval for (`kernel/filing.py`), and the refusal above names that route by asking the kernel for it rather than by carrying a copy of the command name. That command line is NOT among the ones this gate refuses a subagent (it neither orders work nor reinstalls the layer), so a specialist can run it — and what bounds it is the approval and not the caller: the rule it writes is the one the USER minted, field for field, and no command mints. Said here because an unspoken permission is one nobody weighs. Plus `gate_write_scope` (V2, II.4 gate 3): ANY tool write into `project_memory/**` (one writer, the kernel; an agent gets only `staging/<its task-id or root-id>/`), a bound specialist writing outside its `allowed_scope` and an UNBOUND subagent writing anything — both with ONE exception, rule 6: a subagent's OWN `agent-memory/<its role>/` craft topics, and only for a call whose content `guard_memory_budget` really judges (`gate_write_scope._own_craft_memory` and `guard_memory_budget.judges_this_write` are the two halves; read them there). And from a shell, when the caller is a SUBAGENT: the harness subcommands that ORDER work — creating a task, or leasing one for a spawn — and the ones that REINSTALL THE ENFORCEMENT LAYER, i.e. run the kit's installer over this project and rewrite its hooks, settings and role set. `gate_write_scope._ORDERING_COMMANDS` and `_INSTALLING_COMMANDS` are the two sets — read them there rather than from a list here — and a test derives each from the kernel's own routes — to the task producers, and to the one place the installer invocation is built — so a third command of either kind is covered the day it ships. A subagent's own `submit-result`/`evidence` stay open, and so does ASKING the user for the approval such an install needs (no command mints; the user does). Plus, for every caller, naming `project_memory` or the enforcement layer in anything but a read-only command (so copying the hooks elsewhere is refused, reading them is not). Plus `guard_no_adhoc`: the ad-hoc status/summary/result files item 1 forbids, on the `Write` tool, for YOU and every specialist. Plus `guard_pm_scope`, for YOU ALONE (it skips every call carrying an `agent_id`, i.e. every subagent): a write of PRODUCTION CODE — a file in a programming LANGUAGE outside your own areas (`project_memory/**`, `.claude/**`, `plans/**`, `docs/**`, root config/markdown). The language decides, not the directory: measured rc 2 for `tools/sales_extract.py` AND `dashboards/build.js` — both the office-developer's (§2.1) and both to delegate — and for `scripts/euer_report.py` — the renderer item 4 says produces the reports, so a hand-written report is the wrong artifact before it is the wrong writer. `dashboards/sales.html` and `reports/euer_*.md` are not a programming language and pass. Both of those act on the Edit/Write TOOL call. A write performed from a SHELL meets `gate_write_scope` instead, and only where the shell itself lands the bytes: a REDIRECT into production code is refused for YOU by the same file property (`>`, `>>`, `>|`, `&>`, and the csh `>& file`), judged by shell syntax and never by a verb. Among what it does NOT reach — named, not closed: a write a TOOL performs from inside its own language or arguments (`cp`, `mv`, `tee`, `sed -i`, `python -c`, and the PowerShell `Out-File`/`Set-Content`/`Add-Content`/`Tee-Object` cmdlets), and a redirect target built by an expansion this process cannot resolve (`$(…)`/backticks, or a variable the same line does not assign — a same-line `F=…; > $F` IS resolved and refused). Held in both directions by `tools/test_hooks.py::test_the_shell_writes_no_command_line_can_decide_stay_the_named_residue` and `…::test_a_powershell_cmdlet_write_is_the_named_residue_too` |
| `gate_second_reading` + `record_filing_reading` | a document ENTERING the archive on ONE opinion (FR-0035, the user's own words: nothing moves until a name has been assigned and a second independent run arrives at the same answer). It runs behind `gate_filing` in one chained command; the ORDER is NOT load-bearing there and `settings.json` says why, so each gate answers its own question. What it refuses: a landing under `archive/` that is an ENTRY, unless the project holds as many classification readings as the covering rule asks for, all naming THIS document as `source` AND that FULL path — filename included — as `destination`, from that many DIFFERENT attested runs. Disagreement is refused with BOTH readings printed side by side (source, destination, class, run, record file), because that is the pair the USER decides between; nothing is moved and nothing renamed meanwhile. **What counts as an ENTRY**, as a property and not a list: everything landing under `archive/` except a document that comes from inside the archive, is covered by the SAME `path_template`s and keeps the SAME filename. That exemption is the RULE and the NAME, not the FOLDER, and it is therefore wider than "a folder was tidied": a move that changes only a placeholder's value (`…/incoming_invoices/2026/x.pdf` to `…/2027/x.pdf`) is exempt although the year is part of the classification — a gap named here and not closed, and still far narrower than the state before FR-0035, where EVERY archive-internal move was free. An archive-internal RENAME is therefore an entry and needs its own readings; measured 2026-08-29, while it was not, one honest double-read filing opened the whole archive as a free namespace (the same document moved to another rule and back under a forged name, both rc 0). `guard_fs_tripwire` does NOT cover that and never did — its own header records the 2026-08-03 measurement that made refusing archive-internal moves a defect — so this is the only place the question is asked. A landing with NO document behind it (a redirect, a tool write, a move whose source this reader cannot place) is refused outright rather than judged against the readings that happen to name its target: those are consent about a DOCUMENT, never a standing licence for a path. **The conditions under which it does not refuse at all**, all four: a move inside the archive under the same rule and the same name; a destination no plan rule covers (`gate_filing` already refused it, and this gate stays silent so a role meets one message); a covering rule carrying `second_reading: false`, which asks for ONE reading instead of two and NEVER for none — that field is the only release, and `readings_required` treats absent, `true`, a word or a list alike as "two", so the spellings that release are the ones PyYAML reads as the boolean false and not a list in the hook; and of course the readings being there and agreeing. Where two rules cover one place the HIGHEST demand wins. A reading is a `filing_reading` record (`kernel/schemas/filing_reading.yaml`) under `staging/<TSK-ID>/`; ONE record may carry a whole inbox drop, so a second reader costs one run and not one run per document. `record_filing_reading` (PostToolUse, never blocks) is what makes readings countable: for the records THIS call names — read through the same two readers the filing wall uses — it stamps the record's BYTES with the run the provider gives in `agent_id`, and the BYTES of every document the record names as a source, into `project_memory/.filing/readings.jsonl`, inside the state directory and outside `staging/`, so `gate_write_scope` refuses every tool write and every write-capable shell line naming it (measured rc 2 for a `Write`, for an append redirect into that file, and for the same append behind a `cd project_memory`). The document digest is what stops a reading from covering a document swapped in behind it: nothing in this kit refuses an OVERWRITE of an inbox document, only a delete (measured rc 0 three ways). **What "independent" means here, exactly**: two runs, as the provider names them — NOT that the second run had not seen the first. Nothing in the hook layer observes a Read, the records lie in `staging/` where every role may look, and no refusal claims otherwise. Three further limits, named and not closed: a record produced INSIDE another program (`python -c "open(...).write(...)"`, a script) is named by neither reader, carries no attestation, is not a reading and refuses the filing; a document past `_readings.MAX_DOCUMENT_BYTES` gets no digest and its filing is refused rather than filed unbound; and an `agent_id` reused across two spawns would make two genuine readings read as one run — also a refusal, so the unmeasured direction fails safe |
| `guard_fs_tripwire` | a shell command that DELETES something whose resolved position is under `inbox/` or `archive/`, and one that MOVES a document whose resolved source is under `archive/` to a destination outside it. Both halves are about where the operands land, not about the word `archive` appearing in them: a move that stays inside the archive is reorganisation and passes however it is spelled, and a `cd` into the archive followed by a relative move or delete does not hide either one. A move INTO the archive is filing and is `gate_filing`'s question, not this guard's. **That wall has exactly ONE door, and it is the user's** (FR-0050): a live `filing_correction` approval, minted through the ordinary approval flow, lets through the one operation it names — the same document, the same VERSION of it (the manifest hashes the file's bytes), the same destination, or the same deletion. The door opens for a COMMAND LINE and checks four things about it, all of them measured: this guard placed EVERYTHING on the line (every invocation is a directory change it could compute, or a copy/move or delete it read; every operand of those is a token whose text IS the path; and every output REDIRECT target is read too, wherever on the line it stands, since `>` is shell syntax and no reader of arguments sees it — a redirect written FIRST used to hide its own invocation from every reader); the line asks for no more corrections than `guard_fs_tripwire.CORRECTION_CAP` (a bound on the work a gate may do while deciding — the budget is `_compat.HOOK_DEADLINE_SECONDS`, and an unbounded refusal is a session that stands still for as long as the command line is); every operation carries its own live approval; and each approval names that operation exactly. An invocation this guard does not read (`python -c`, `tar --remove-files`, an `echo`, a `tee` behind a pipe), an operand or redirect target the shell rewrites (`$VAR`, a glob, `~/…`) or that names no place in the project, a `cd` it cannot follow, a redirect writing INTO `inbox/` or `archive/`, a second unapproved document, a destination outside the project, or a delete it could read only from the raw command text — any one of them and NOTHING on that line is let through. **All four decide the DOOR, never the WALL**: what this guard never saw it still never sees, so a `python -c "os.remove(…)"`, or a bare output redirect into one of those trays, alone on its own line, is refused by nothing here — exactly as before the door existed. What the approval covers is those bytes at that position while they lie there, so it stops covering the document once the correction has run, and covers a byte-identical file put back at the same position. What it does not see: a removal performed inside another program, and an operand the shell rewrites before use (a variable, a glob, `~`) — uncertainty leaves the command alone. Plus `gate_push_token` (R1): `git push` needs a user approval minted through the approval flow and bound to remote+branch+HEAD — a new commit invalidates it. That token cannot cover a FORCE push, because it binds the commit and not the remote's history, so this gate refuses one outright — on `_compat.names_force_push`, so `--force`, `-f`, `--force-with-lease` and a `+refspec` are one rule and not four (a `--dry-run` does not excuse it, and it is refused before the approval is even looked up). This kit installs no second git gate, so that refusal is the whole rule here. Plus `gate_shell_hygiene` (R10/R11): destructive `docker` on a FOREIGN compose project or any `prune`; merge/rebase/pull/`reset --hard`/branch-switch on a dirty tree (`git add`/`stash`/`checkout -b` stay open) |
| `guard_question_context` | user questions referencing INVISIBLE context ("wie oben zusammengefasst" — thinking/tool calls are unseen); questions must be self-contained or preceded by visible text. Plus THREE non-blocking WARNINGS on the same event (exit 0, stderr + an audit note): a question to the user full of technical vocabulary (R2), one that asks the user for something only the MACHINE has — a git identity, the window's title bar (R2b, from a measured pilot escape), and a masterplan approval that offers no risks or objections (R13). All three are word nets over the question's own text, and that cuts both ways: a technical question phrased without such a word passes, and a PRODUCT question that uses one of them in its own sense can warn — R2b's second tier -- the words this repo has MEASURED inside a real product question, kept in the hook beside this file (`guard_question_context._AMBIGUOUS_VOCAB_RX`) and not as a copy here -- needs two hits for exactly that reason, and a single one of them no longer says anything at all. Ignore a note whose word is genuinely yours; the constitutional rule stays yours to keep either way. A question carrying the kernel's `[APR-REQ:<id>]` marker is exempt from the three, because its wording is the kernel's and must be relayed verbatim. Plus `gate_approval` (V2, spec II.2): a question marked `[APR-REQ:<id>]` must match the kernel-generated approval question EXACTLY (text, header, every option) or it is blocked; only the verbatim `Freigeben [code]` label mints the approval |
| `guard_yaml_valid` | invalid `project_memory/*.yaml` at write time — well-formedness only (parse errors, duplicate keys); what an item must CONTAIN is its TYPE's field contract, which the state validator answers (`python scripts/harness.py validate`) Plus `guard_memory_budget` (V2, spec II.5): a MEMORY.md index over 40 lines / 8 KB, a craft topic over 100 lines / 8 KB, any OTHER file in agent-memory over 8 KB, a 21st topic for one role, or ANY project item id in a role's memory — memory holds craft, never project status (put an id in `backticks` to quote it) |

| `notify_agent_events` / `session_status` / `kit_trust_state` / `clear_handover_marker` | (never block) lifecycle audit log / session-start briefing incl. inbox count, due reports, stale compliance entries, kit-update + model/effort nags / records which hook bundle this project trusts in `.claude/kit_state.json` (`restart_required` -> `active`; `hooks_trust_required` when the bundle changed) -- doctor measures `hook_trust` against it, and `gate_dispatch` REFUSES every specialist spawn while the installed bundle is not the recorded one (it compares the hashes itself, so a bundle changed mid-session counts too; `restart_required` is not that case and delegation stays open there). ANY difference counts, a stray `.pyc` cached into `.claude/kernel/__pycache__` included -- measured: one such file stops every delegation, and removing that `__pycache__` directory restores the recorded hash on its own (bytecode is not part of what the scaffold installs). A project carrying NO `kit_state.json` has nothing to compare and is not stopped. Touching the record is refused on every route that NAMES the layer -- Edit/Write by `guard_harness_selfmod`, and a shell pipeline by `gate_write_scope` (measured for `rm`, `rm -f`, `del`, `Remove-Item`, an inline `os.remove` and `cd .claude && rm`).
