# 05 — FR-0080: Umsetzungsplan und Mindmap als `.drawio.svg`, generiert

Die Recherche hat die Grundfrage beantwortet (`docs/research/2026-07-27-plan-als-diagramm.md`:
generiert, reines Python, SVG-Geometrie und `<mxfile>` aus einem Layout-Durchgang). Hier steht,
**welche** Sicht der Plan ist, **welche** die Mindmap, aus welchen Feldern beide entstehen, und wie
eine Handänderung erkannt wird — mit einem Prototyp, der an echten Items dieses Repos läuft
(`make_diagrams.py`, Ausgaben in `diagrams/`, Bilder `review/diagram-*.png`).

## Befund zum Format im Repo, gemessen

- Das Hauptrepo trägt **keine** `.drawio.svg` (weder WFR noch ARC; `find` über den Baum: 0 Treffer). Was FR-0080
  „bereits in Gebrauch" nennt, ist das Format in `kernel/staging.py` und in den Pilotprojekten:
  `C:\Offline Repos\v2-testbed\dev-app\project_memory\architecture\active\ARC-0001.drawio.svg` (545 Byte).
- Die einzige Prüfung, die der Kernel an ein `.drawio.svg` legt, ist `staging._assert_xml_wellformed` =
  `ET.parse`. Gemessen (`measure_wellformed.py`): sie **besteht** für die drei erzeugten Dateien **und** für die
  Pilot-Datei — die aber **kein `content`-Attribut** trägt, also für draw.io ein Bild ohne Modell ist. Der
  Name `render_check: True` in der Begleitdatei behauptet weiter mehr, als geprüft wird (so steht es schon in
  der Recherche); dieser Strom ändert `staging.py` nicht (C).

## Die zwei Bilder

| | Plan `generated/plan.drawio.svg` | Mindmap `generated/mindmap.drawio.svg` |
|---|---|---|
| Frage, die es beantwortet | „Welche Schritte sind nötig, und wo stehen wir?" | „Was gehört wozu?" — die Sicht, in der Missverständnisse auffallen (Wunschliste §3a) |
| Form | Raster: **eine Zeile je Wurzel**, drei Bahnen `planned · in flight · done`; jedes Item unter der Wurzel steht in der Bahn, die sein eigener Status ergibt (`lane`, wie auf der Tafel) | Baum nach rechts: Projekt → Wurzeln → Art der Dinge (`backlog_tree.label`, je `area` eine Gruppe — FR-0017) → die Dinge |

| Wörter | Klartext: „bug: …", „task: ui for SR-0009 · …", Bahnen in Worten; Ids klein davor, kein Status-Vokabular | dito; jedes Blatt trägt seine Bahn **als Wort** („— in flight"), nicht nur als Füllung (WCAG 1.4.1, Sichtrunde 4) |
| Layout | Multiplikation: Spalte × Breite, Zeile × Höhe; kein Layout-Algorithmus | dito, Blätter gestapelt, Eltern mittig zu ihren Kindern |
| Farben | eine benannte Palette (`INK`, `PAPER`, `RULE`, `LANE_FILL`), sonst kein Hex im Generator | dieselbe |

Beide Dateien: `<svg …>` mit der Geometrie **und** `content="&lt;mxfile …&gt;"` (draw.io-Modell,
unkomprimiert: `mxCell`-Knoten mit `mxGeometry`, orthogonale Kanten) aus **einem** Durchgang (`Sheet`).
Gemessen: Plan 34 SVG-Elemente / 21 Zellen, Mindmap 42 / 29; Chromium rendert beide ohne Fehler

## Auslöser: derselbe wie das Board — und das ist ein Seam

Das Board entsteht in `state._regenerate_index_locked` → `state._write_board` (fail-soft, ein `try`).
`state.py` ist C-Eigentum. Die **eine** Zeile, verbatim für das Protokoll:

```python
# in ProjectState._write_board, innerhalb desselben try, nach board.render:
for name, text in plan_diagram.render_all(self, entries):
    self._write_text_atomic(self.generated_path(name), text, errors="replace")
```

plus `from . import board, plan_diagram` in `state.py` und die Nennung der zwei Pfade in
`cli.py` beim `generate-index` (heute druckt es Index und Board). Bis der Seam angewendet ist, ist
„regenerated by the same trigger as the board" **nicht wahr** und wird nirgends behauptet; Phase 2 liefert
das Modul, die Tests und diese Zeile — und
`test_board.test_no_kernel_writer_of_a_rendered_file_leaves_the_board_behind` (leitet die Schreiber aus dem
Paket ab) ist nach dem Merge der Test, der die Behauptung dann trägt, um `plan_diagram` erweitert.

Das Modul heißt `team-kits/kernel/plan_diagram.py` und sonst nichts im Kernel (Item). Schnittstelle:
`render_all(state, entries) -> [(filename, text), ...]`, `is_pristine(path, entries) -> (verdict, reason)`,
`digest_of(entries)`.

## Handänderung erkennen — gebaut und gemessen im Prototyp

Die Datei ist eine **reine Funktion der Entries** (keine Uhr, keine Zufalls-Ids; zwei Läufe → gleiche
Bytes, gemessen `True`). Die Wurzel trägt `data-source-digest` = SHA-256 über die kanonische
Liste `(id, type, status, title, parents)`. Damit unterscheidet `is_pristine` drei Fälle, alle gemessen:

| Fall | Herstellung | Urteil |
|---|---|---|
| unberührt | Datei wie geschrieben | `pristine` — Bytes gleich einem frischen Render |
| von Hand geändert | ein `<text>` per ElementTree ergänzt, so wie draw.io beim Speichern das Dokument neu schreibt (`plan-hand-edited.drawio.svg`) | `hand-edited` — gleicher Digest, andere Bytes |
| veraltet | dieselbe Datei gegen Entries, in denen ein PR-Status verschoben ist | `stale` — anderer Digest |

Wer prüft es, und wann: (a) der Test `test_plan_diagram.test_a_hand_edit_is_told_from_a_stale_file`
(Phase 2, in unserem Scope); (b) im laufenden Projekt **niemand von selbst** — die Datei liegt unter
`generated/` (ignoriert, nie committet), wird beim nächsten Zustandsschreiben überschrieben, und
zwischen zwei Schreibvorgängen sieht kein Gate eine Handänderung. Das ist der Lochkandidat für
Phase 2 (`04-build-spec.md` §6): ob `report.validate_state` (C) `is_pristine` als Warnung meldet, ist ein
Seam-Vorschlag, keine Zusage.

## Ablage: `generated/`, nicht committet — gegen §3a, und darum eine Frage an dich

Wunschliste §3a empfiehlt „mitcommittet mit Frischeprüfung", weil ein frischer Clone das Bild sofort
zeigen soll. FR-0080s Abnahme verlangt das nicht („generiert, nie von Hand, derselbe Auslöser, Handänderung
erkannt"). Beides zusammen kostet ein Gate, das Diff und Bild vergleicht, in einem Verzeichnis, das
heute jedes Kit ignoriert (`templates/repo/.gitignore`: `project_memory/generated/`). Der Prototyp legt die
Dateien nach `generated/` neben das Board. Frage 5 in `user-feedback.md`.

## Was der Prototyp offen lässt, benannt

- Der Plan zeigt die **Kinder** einer Wurzel in Bahnen; die Wurzel selbst steht links ohne Bahn (ihr Status ist
  in ihrer Kartenfarbe nicht kodiert). Phase 2: Wurzelzelle trägt ihre Bahn als Wort.
- Texte werden bei 58 Zeichen mit „…" gekappt (`clip`); die vollständigen Titel stehen in der Tafel.
- Kein `mxfile.xsd`-Abgleich (die Recherche nennt ihn): keine Netzabhängigkeit im Prototyp; Phase 2 kann das
  Schema als Fixture beilegen, wenn der Nutzer es will — bis dahin bleibt die Prüfung „ist XML, trägt ein
  `mxfile`-Modell mit Zellen".
- Ein Projekt mit 284 Items (dieses) ergäbe einen Plan mit 284 Zellen — kein Größenbudget im Prototyp;
  Phase 2 setzt eines je Datei (die Recherche: „max. N Knoten") und sagt auf dem Bild, was fehlt.
