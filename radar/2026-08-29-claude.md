## Highest-impact

### 1. **A UTF-8 BOM at the start of an agent / skill / command `.md` made Claude Code silently ignore the whole file — FIXED (2.1.239)** — this is a way for a *gate role definition or a harness role* to not bind at all, invisibly, on any client below the fix
- **Source**: changelog https://code.claude.com/docs/en/changelog — 2.1.239 (Aug 21): *"Fixed
  agents, skills, and commands whose `.md` file starts with a UTF-8 BOM being silently ignored"* ·
  seen 2026-08-29
- **What it is**: Before 2.1.239, a leading byte-order mark (`EF BB BF`) on a definition `.md` file
  made Claude Code drop the file **without any error**. An editor or a Windows tool can add a BOM on
  save without the author noticing.
- **Why it helps this repo**: The harness's whole enforcement story is **role `.md` files that must
  load**: `.claude/agents/harness-implementer.md` / `harness-verifier.md` carry the two writing
  roles; `gate_spawn_needs_item.py` reads a role's frontmatter (`harness_item: none`) to decide a
  spawn; the kits ship every specialist as an `agents/*.md`. A **silently-ignored** role file means
  the role the constitution relies on isn't there — the `agent:` binding falls back, or a spawn the
  gate meant to police has no definition to read. This is the same failure class as the
  2026-08-16 item 3 (`project_memory/` cleanup) and the BOM detail is nasty precisely because it is
  **invisible on inspection** and host-tool-induced. I checked the repo's own role files for a BOM
  via read tools (the shell `find` over `team-kits`/`.claude` is itself an H19 gate over-refusal, so
  this was a read-tool scan): **none of the sampled role `.md` files carry a BOM today** — so no
  live breakage, but nothing *prevents* a future save from adding one on a client < 2.1.239.
- **Recommendation**: **adopt (cheap, two-part)** — (a) add a one-line **CC-floor note** ("role /
  skill / gate `.md` files load only without a leading UTF-8 BOM; CC ≥ 2.1.239 also no longer
  silently drops a BOM'd file") to the same install/`HARNESS_LOG` floor note the prior reports keep
  proposing; (b) add a **structural test** asserting no tracked `.md` under `.claude/agents/` and the
  kit `agents/` trees begins with `EF BB BF` — a both-ends tripwire per house rules, so a BOM
  introduced by a future editor save can't silently un-bind a role. ~30–45 min. · **Status**: NEW

### 2. **Built-in permission matcher no longer misfires on `$()` / backtick command substitution in Bash `if` conditions (2.1.243)** — Anthropic hardening the exact command-substitution blind-spot the kit's `gate_commit_evidence` / `_harness.command_line` reasons about (TSK-0019, H22); validation plus concrete vectors to mine
- **Source**: changelog https://code.claude.com/docs/en/changelog — 2.1.243 (Aug 24): *"Fixed hook
  `if` conditions like `Bash(cat *)` firing on unrelated Bash commands that contain a `$()` or
  backtick substitution"* · seen 2026-08-29
- **What it is**: CC's own permission/hook-`if` matcher was **over-matching** — a command that merely
  *contained* a command substitution could trip a rule meant for a different command. The fix makes
  the matcher parse substitutions rather than pattern-match across them.
- **Why it helps this repo**: This is the precise seam the harness works in. `gate_commit_evidence`
  already classifies a command whose tree is changed by **a command a substitution introduces**
  (`_harness.command_line`, added in TSK-0019); the constitution names **H22** (a write the kits'
  classifier reads as a read) as a measured, still-open hole in the same family. Anthropic finding
  and fixing a **command-substitution matcher bug in its own checker** is (a) independent validation
  that "the checker tokenizes command substitution differently from the shell" is a real, active
  evasion/false-match class, and (b) a concrete case to lift into `test_gates.py`: does the kit
  matcher **over-match** (a benign line refused) or **under-match** (a writing line let through)
  when a `$()`/backtick substitution is present but not the operative command? The gate's own
  refusal-vs-pass behaviour on such a line should be measured, not assumed.
- **Recommendation**: **adopt (evaluate)** — in a throwaway clone outside the repo, feed
  `gate_commit_evidence` / `gate_lead_write_scope` command lines that carry an *unrelated* `$()` or
  backtick substitution (both a benign-read case and a hidden-write case) and record whether the
  classifier over- or under-reads; log any under-read as a measured hole in
  `docs/POST_V2_WISHLIST.md` with the chain, or note the gate already covers it. ~1–1.5 h. ·
  **Status**: NEW

### 3. **New prompt-cache-TTL surface: `promptCacheTtl` / `subagentPromptCacheTtl` settings (2.1.243) and per-agent `experimental.cacheTtl` frontmatter (2.1.248)** — a source-format widening (a new frontmatter field + new settings keys) the Codex generator and any schema check must knowingly accept or reject
- **Source**: changelog https://code.claude.com/docs/en/changelog — 2.1.243 (Aug 24): *"Added
  `promptCacheTtl` and `subagentPromptCacheTtl` settings … keep a 1-hour prompt cache on the main
  conversation while subagents stay 5 minutes"*; 2.1.248 (Aug 27): *"Added `experimental.cacheTtl`
  (`"5m"` or `"1h"`) to agent frontmatter: per-agent prompt cache TTL used when no subagent TTL
  setting is configured"* · seen 2026-08-29
- **What it is**: Three new knobs controlling how long the prompt cache lives — two `settings.json`
  keys and, newly, a **field inside an agent `.md` frontmatter** (`experimental.cacheTtl`).
- **Why it helps this repo**: The **source-format duty** watches exactly this contract — frontmatter
  fields + `settings.json` schema are the Claude-native source the **Codex layer is generated from**.
  `experimental.cacheTtl` is a **new frontmatter key**: the generator and any role-frontmatter
  schema/round-trip check must either carry it across or deliberately drop it as Claude-only, not
  silently choke on an unknown key. No kit role sets it today (checked via read tools — no
  `cacheTtl`/`experimental` in any kit `agents/*.md`), so **no exposure now**; the flag is only that
  the source contract widened again. Cost/behaviour angle is minor for the kits (they don't set it),
  but note the *default* — subagents cache at 5 min while the lead holds 1 h — means a re-spawned
  specialist re-pays its cache write; irrelevant to correctness, noted only for completeness.
- **Recommendation**: **watch / source-format flag** — confirm the Codex generator tolerates an
  unknown frontmatter key (or explicitly rejects `experimental.*`), and add `experimental.cacheTtl`
  to the list of known-Claude-only frontmatter the source-format duty tracks. No kit edit. ~15–20 min
  to confirm the generator's behaviour. · **Status**: NEW

### 4. **Subagents dying on a first-call model 404 now fall back to the session model chain instead of erroring out (2.1.247, 2.1.248)** — strengthens the case for last week's `model:`-pin structural test: a role whose pinned alias 404s no longer fails loudly, it silently rides the fallback
- **Source**: changelog https://code.claude.com/docs/en/changelog — 2.1.247 (Aug 26) & 2.1.248
  (Aug 27): *"Fixed sub-agents dying on a first-call model 404: they now use the session's fallback
  model chain; the error returned to the parent includes the error type, status, request id, and
  model"* · seen 2026-08-29
- **What it is**: A subagent whose pinned model returns 404 on the first call used to die; now it
  **falls back to the session's model chain** and continues (the 404 detail is surfaced to the
  parent, not swallowed — better than before, but the run still proceeds on a *different* model than
  the role pinned).
- **Why it helps this repo**: This lands on the same nerve as last week's **item 2** (the removed
  "Default teammate model" setting). The kits tier every role via frontmatter (`worker`/`lead`/
  `fable`), and the harness roles pin `opus`. If a pinned alias ever fails to resolve (a rename, a
  retirement, a typo), the platform will now **quietly run that role on the fallback model** instead
  of failing — which is *exactly* the silent-wrong-tier outcome the proposed `model:`-pin test was
  meant to guard against, now with one more way to arrive there (unresolvable pin, not just missing
  pin). The verifier running on the wrong tier is a correctness risk the constitution's three-role
  separation cares about.
- **Recommendation**: **fold into the still-open `model:`-pin test item** (2026-08-21 item 2) —
  broaden that proposed structural test from "every spawnable role carries a `model:` line" to "every
  spawnable role pins a `model:` that **resolves to a known alias/tier** in `model_tiers.yaml`", so a
  pin that would 404-and-fall-back is caught at test time, not at spawn time. ~adds ~20 min to the
  already-scoped item. · **Status**: NEW
