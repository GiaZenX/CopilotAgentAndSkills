## Highest-impact

### 1. **Todo/task-tracking tools removed on Opus 4.8 / Sonnet 5 / Fable 5 / Mythos 5 and newer (2.1.233)** — this is the exact model set the kits' aliases resolve to, so it silently disables `gate_todo_items.py`'s traffic and any kit flow that tracks items via `TodoWrite`
- **Source**: changelog https://code.claude.com/docs/en/changelog — 2.1.233 (Aug 14): *"Todo/task-tracking
  tools (TaskCreate/Get/Update/List, TodoWrite) are no longer available on Opus 4.8, Sonnet 5, Fable 5,
  Mythos 5, and newer models; set `CLAUDE_CODE_ENABLE_TODO_TOOLS=1` to bring them back"* · seen 2026-08-16
- **What it is**: On the current-generation models, the `TodoWrite` tool (and the `Task*` family) is **off
  by default**. It only comes back with the `CLAUDE_CODE_ENABLE_TODO_TOOLS=1` env flag.
- **Why it helps this repo**: The harness has a **fourth gate built entirely around `TodoWrite`** —
  `gate_todo_items.py` fires on `TodoWrite` and refuses "a task list with more than one entry without an
  item id, or with an id that leads to nothing open" (see the gate table in `CLAUDE.md`). The
  constitution's own "Wo Dinge hingehören" table also assigns the **session task list** a load-bearing
  role ("genau einer darf dort ohne Item-Id stehen"). The kits pin the `opus` / `sonnet` aliases, which
  resolve to **exactly** the models in this list (Opus 4.8, Sonnet 5). So out of the box on a current
  client, `TodoWrite` never fires → **`gate_todo_items.py` has zero traffic to gate, and the session
  task-list discipline the constitution relies on has no tool behind it.** This is not a hole in the gate;
  it's the gate's input disappearing. If the harness wants the task-list workflow and its gate to keep
  meaning something, the kits must set `CLAUDE_CODE_ENABLE_TODO_TOOLS=1` in `settings.json` `env`.
- **Recommendation**: **adopt** — add `"CLAUDE_CODE_ENABLE_TODO_TOOLS": "1"` to both kits' `settings.json`
  `env` block so `TodoWrite`/`gate_todo_items.py` stay live on current models; add a one-line test that
  the flag is present (a both-ends tripwire, per house rules). Alternatively, if the harness decides the
  task list is no longer the tracking surface, retire `gate_todo_items.py` deliberately rather than leave
  a gate guarding a tool nobody calls. Either way it's a **decision**, not drift. ~30–60 min. · **Status**: NEW

### 2. **Subagent forking is on by default (2.1.232): a `fork` subagent inherits the FULL parent conversation + prompt cache, and non-teammate spawns run in the background by default** — lands directly on the verifier's "clean item-derived brief, read-only copy outside the repo" isolation and on the anti-re-delegation invariant
- **Source**: changelog https://code.claude.com/docs/en/changelog — 2.1.232 (Aug 13): *"Subagent forking
  is now on by default: a `subagent_type: "fork"` subagent inherits the full conversation and prompt
  cache, and non-teammate agent spawns in interactive sessions now run in the background by default"* ·
  seen 2026-08-16
- **What it is**: A new spawn mode where the child inherits the **entire parent context** (conversation +
  cache) instead of starting from a clean brief, now the **default** for a `fork`-typed spawn. Separately,
  ordinary (non-teammate) agent spawns now default to background.
- **Why it helps this repo** (two seams, both real):
  1. **Isolation seam.** The constitution's central rule is that *"Der Auftrag an den Umsetzer wird aus
     dem Item erzeugt, nicht frei geschrieben"* and the Prüfer works *"read-only in einer Kopie außerhalb
     des Repos."* A **fork inherits the full conversation** — the opposite of a clean, item-derived
     brief. If any kit role is (or becomes) a `fork` spawn, the implementer/verifier no longer starts
     from the item; it starts from whatever the lead's context happened to contain. That directly
     undercuts the "item is the input, not the message" discipline. Worth an explicit check that no kit
     role definition uses `subagent_type: "fork"`, and a note in the roles doc that forking is banned
     for the two writing roles.
  2. **Anti-re-delegation / background seam.** Non-teammate spawns going background-by-default is the same
     surface as V14a (`run_in_background` delegation default + never advance phase before all
     notifications) and the `guard_agent_spawn` / `deny: Agent(project-manager)` invariant. The
     background default is now the platform's, not just the kit's — reconfirm the kit's own guard is still
     the primary gate and the notification-drain rule still holds when the platform, not the kit, chose
     background.
- **Recommendation**: **adopt (evaluate)** — grep all kit role `.md` frontmatter for `subagent_type`/`fork`;
  if absent (likely), add a structural test asserting no writing role forks, plus a one-line roles-doc ban.
  Fold the background-default reconfirmation into the still-open depth-pin item. ~1–1.5 h. · **Status**: NEW

- **Source**: changelog https://code.claude.com/docs/en/changelog — 2.1.228 (Aug 11): *"Fixed session
  cleanup deleting contents inside a project's memory folder"* · seen 2026-08-16
- **What it is**: Before 2.1.228, Claude Code's session-cleanup path could delete files **inside a
  project's memory folder**.
- **Why it helps this repo**: The harness keeps its entire canonical state in **`project_memory/`** —
  decisions, evidence (`EVD-*` with the diff-hash that `gate_commit_evidence.py` reads to allow a commit),
  items, staging. The constitution is explicit that *"Was ausschließlich in einer Aufgabenliste oder in

  nachweislich passiert."* A platform bug that **deletes memory-folder contents on session cleanup** is
  precisely the failure mode that rule was written against — on a client **< 2.1.228** an idle/cleaned-up

  enforcement story, and it argues for the CC-floor note the prior reports keep proposing.
- **Recommendation**: **adopt** — add a one-line CC-floor note to the install docs / `HARNESS_LOG`

### 4. A second **shell/path permission-bypass cluster** (2.1.232–2.1.233) — same evasion class as the harness's command-line gates, and this batch is Windows-host-specific (this repo's host)
- **Source**: changelog https://code.claude.com/docs/en/changelog —
  **2.1.232** (Aug 13): *"Fixed a PowerShell permission bypass where variable-writing parameters could
  silently overwrite `$PSDefaultParameterValues` and redirect later commands' file access"* · *"Fixed a
  Windows permission bypass where Git Bash followed Cygwin-style symlinks that path validation saw as
  regular files"* · *"Fixed nested git repositories inheriting trust from a parent directory"*;
  **2.1.233** (Aug 14): *"Fixed Windows paths spelled with the NT `\??\` device prefix bypassing UNC path
  validation, closing an NTLM credential-leak vector"* · seen 2026-08-16
- **What it is**: Four more platform fixes in the same family last week's item 1 flagged — a command line
  or path crafted so the **permission checker sees less than the shell/OS executes** (PowerShell default-
  parameter redirection, Git Bash Cygwin symlinks, cross-repo trust inheritance, NT device-prefix paths).
- **Why it helps this repo**: This is the terrain `gate_lead_write_scope`, `gate_commit_evidence`,
  `_harness.command_line` and `_harness.ProtectedArea` operate on — they tokenize a command line and
  resolve paths to decide write-scope. The repo already tracks Windows path-resolution holes in exactly
  this family (**H19** ancestor paths, **H20** POSIX-absolute `cd` the gate can't follow, **H33** tilde
  prefixes). The **PowerShell `$PSDefaultParameterValues`** fix is a fresh vector for the *PowerShell* half
  of the gates' matcher (the gates match Bash **and** PowerShell per V11); the **NT `\??\` device prefix**
  and **Cygwin symlink** fixes are Windows path-resolution vectors the `ProtectedArea` resolver should be
  checked against, since this repo's canonical host is Windows. Anthropic finding and fixing the same class
  in its own checker is (a) validation that the harness's blind-spot list is the right list and (b) four
  concrete strings to lift into `test_gates.py` — noting the seam last week already named: these harden
  Claude Code's **built-in** checker, **not** the kit gates, so they do **not** close kit holes for free.
- **Recommendation**: **adopt (evaluate)** — mine the four cases as `gate_lead_write_scope` /
  `gate_commit_evidence` vectors (esp. the PowerShell default-param redirection against the PowerShell
  matcher, and NT `\??\` / Cygwin-symlink against `ProtectedArea`); where the kit tokenizer/resolver
  under-reads, record it as a measured hole in `docs/POST_V2_WISHLIST.md` rather than claiming coverage.
  ~1–2 h. · **Status**: NEW
