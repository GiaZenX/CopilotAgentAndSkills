## Highest-impact

### 1. Nested-subagent default REVERSED to depth 3 (2.1.219) — last week's "no-nesting is the platform default" (item 2) is NO LONGER TRUE; the runtime anti-re-delegation backstop is gone by default, and specialist `tools:` hygiene is now load-bearing
- **Source**: changelog https://code.claude.com/docs/en/changelog — 2.1.219, Jul 24, 2026 (*"Subagents
  can now spawn nested subagents up to depth 3 by default (was 1); set
  `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=1` to disable nesting"*) · **verified against the official doc**
  https://code.claude.com/docs/en/sub-agents (*"By default, a subagent can spawn subagents of its own,
  **up to three layers below the main conversation**"*; version-history: *"v2.1.172–2.1.216: nest by
  default up to five layers … the limit couldn't be changed"*) · seen 2026-08-01
- **What it is**: The subagent-nesting default has now flipped **twice** in two weeks: ≤2.1.216 = 5
  layers (unchangeable) → **2.1.217 = 1 (no nesting)** → **2.1.219 = 3**. Last week's item 2 celebrated
  the 2.1.217 state ("no-nested-subagents is now the platform DEFAULT … a specialist fan-out loop is
  now blocked three ways"). As of 2.1.219 the platform **again allows** a subagent to spawn subagents
  up to depth 3 out of the box.
- **Why it matters here**: This lands on the harness's **anti-re-delegation** invariant
  (`guard_agent_spawn` + V14b `deny: Agent(project-manager)` + the constitution's "no specialist
  spawns a specialist" rule). The **runtime backstop last week counted as free defense-in-depth is now
  off by default** — the kit's prompt+hook layer is once again the *sole* enforcement unless the kit
  opts back in. Two concrete, **verified** consequences:
  1. **A real, sourced remedy exists.** The sub-agents doc shows the exact opt-out: put
     `"CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH": "1"` in the kit `settings.json` `env` block to **turn
     nesting off** and restore the runtime zero-nesting backstop the harness briefly got for free.
     This is the belt-and-suspenders knob last week's item flagged as optional — it is no longer
     optional if you want the runtime backstop.
  2. **Specialist `tools:` hygiene is now the load-bearing control.** The doc (line 878): *"To keep one
     subagent from spawning while nesting is on … **omit `Agent` from its `tools` list or add it to
     `disallowedTools`**"*, and (line 398) a subagent that lists bare `Agent` **can** spawn its own
     subagents while depth allows. So with depth-3 nesting back on, the harness's protection leans on
     **every specialist's frontmatter NOT listing `Agent`**. Spot-checked the repo agents
     (radar-watcher, codex-watcher, harness-implementer/-verifier) — none list `Agent`, good — but this
     should be verified across **all kit specialists** and asserted by a gate/test, because a single
     specialist that gains `Agent` in `tools:` now silently regains fan-out ability.
- **Recommendation**: **adopt** — (a) pin `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=1` in the kits'
  `settings.json` `env` to restore the runtime no-nesting backstop (~15 min), and (b) add a
  structural check that no kit specialist `.md` lists `Agent` in `tools:` (~30 min). · CC floor:
  the env knob is **≥ 2.1.217**. · **Status**: NEW · **supersedes the "confirms design / ignore"
  verdict proposed for 2026-07-24 item 2** — that item's premise (no-nesting is the default) no
  longer holds.

### 2. SubagentStart / SubagentStop are now FIRST-CLASS documented hook events (agent-type matchers) — RESOLVES the standing watch (2026-07-17 item 6, 2026-07-24 item 3b): `gate_subagent_output` can become a per-agent `SubagentStop` frontmatter hook
- **Source**: official hooks reference https://code.claude.com/docs/en/hooks (lists **SubagentStart**
  and **SubagentStop**, matcher = agent type) · official sub-agents doc
  https://code.claude.com/docs/en/sub-agents (frontmatter `Stop` → *"converted to `SubagentStop` at
  runtime"*; `SubagentStop` matcher = agent-type name, scoped names are unanchored regex — anchor with
  `^…$`) · community shape https://www.totalum.app/blog/claude-code-hooks-totalum · seen 2026-08-01
- **What it is**: The per-subagent lifecycle hooks that were an **unverified community lead** for two
  reports are now **official in the hooks reference AND the sub-agents doc** — exactly the verification
  the standing rule demanded ("verify the event name on the official hooks doc before acting"). A
  `Stop` hook in an agent's own frontmatter auto-converts to `SubagentStop` when it runs as a subagent;
  session-wide `SubagentStart`/`SubagentStop` can also be registered in `settings.json`, filtered by
  agent-type matcher.
- **Why it matters here**: The harness's `gate_subagent_output` inspects specialist output and is
  registered **globally** today. It can now be attached **per-agent** as a `SubagentStop` frontmatter
  hook (matcher = the specialist's `name`) — tighter, a cleaner source contract, and it fires exactly
  around that one specialist's lifecycle instead of every subagent. Community write-ups add a concrete
  return shape worth verifying: a `SubagentStop` hook can emit `hookSpecificOutput.additionalContext`
  to inject "tests passed at commit abc123" back to the lead (audit trail) or `exit 2` to bounce the
  specialist back to fix — which is precisely the harness-implementer→harness-verifier loop. The
  sub-agents doc itself now describes this exact pattern ("*a reviewer subagent that dispatches a
  verifier per finding*").
- **Recommendation**: **adopt (evaluate)** the `gate_subagent_output` → per-agent `SubagentStop`
  frontmatter-hook refactor (verify the `additionalContext` field name against the hooks reference
  before relying on it; anchor any scoped matcher with `^…$`) — ~1–2 h if adopted · **watch** the
  `additionalContext` audit-trail channel as an upgrade to the implementer/verifier handoff. · CC
  floor: **≥ 2.1.218** (frontmatter `Stop`→`SubagentStop`). · **Status**: NEW · **resolves** the
  2026-07-17 item 6 and 2026-07-24 item 3b watches.

### 3. Workspace-trust exemption boundary is now precise (refines 2026-07-24 item 3): project-level kit guards are SILENTLY skipped until the install folder is trusted — user-level and `--agents` are exempt
- **Source**: sub-agents doc https://code.claude.com/docs/en/sub-agents (*"To let a project-level
  subagent's frontmatter hooks run, accept the workspace trust dialog for the folder that contains the
  agent file. **Hooks from user-level subagents in `~/.claude/agents/` and from definitions you pass
  with `--agents` run without this step.** … Until you trust the folder, the subagent still runs, but
  Claude Code **skips its frontmatter hooks and logs an error to the debug log**"*) · seen 2026-08-01
- **What it is**: The exact scope rule behind last week's 2.1.218 trust requirement. Project-level
  agents (`./.claude/agents/`) need the workspace-trust grant for their frontmatter hooks to fire;
  user-level (`~/.claude/agents/`) and `--agents`-passed definitions are **exempt**; an `--add-dir`
  folder from outside the trusted repo must be trusted **separately**.
- **Why it matters here**: The global `CLAUDE.md` initializer installs kits into the **project**
  `./.claude/agents/` — the non-exempt scope. So on a **fresh install in an untrusted folder**, every
  specialist runs with its per-agent guards (`guard_no_adhoc`, `guard_guidelines`, `format_on_write`,
  and — per item 2 — any `SubagentStop` gate) **silently skipped**, with only a debug-log line. That is
  a real, quiet enforcement gap, not just a version note. (The repo's own `radar-watcher`/
  `codex-watcher` are project-level too, so the same grant gates their frontmatter hooks.)
- **Recommendation**: **adopt** — a sharpened install/trust note in the install docs + `HARNESS_LOG`:
  "accept workspace trust for the installed `./.claude/` folder or the per-agent guards do not fire;
  user-level agents are exempt but the kit installs project-level." Consider having `harness.py doctor`
  surface untrusted-folder state. ~20 min for the note. · CC floor: **≥ 2.1.218**. · **Status**: NEW ·
  **refines** 2026-07-24 item 3(a).
