## Highest-impact

### 1. **New `--restricted` / `CLAUDE_CODE_RESTRICTED=1` mode (2.1.248) IGNORES user, project and local settings files — which means it silently drops all four of this repo's gates**
- **Source**: changelog https://code.claude.com/docs/en/changelog — 2.1.248 (Aug 27): *"Added
  `--restricted` (or `CLAUDE_CODE_RESTRICTED=1`): removes the built-in tools that run commands or
  code and `WebFetch` (unless named in `--tools`), keeps file tools inside the working directory,
  refuses `bypassPermissions`, and ignores user, project and local settings files"* · seen 2026-08-28
- **What it is**: A new hardened launch mode. It locks down a lot (no Bash/code-execution tools, no
  `bypassPermissions`, file tools confined to the working dir) — **but it does so by ignoring every
  settings file**, including the project `.claude/settings.json`.
- **Why it helps / concerns this repo**: This repo's **entire enforcement apparatus is registered
  in `.claude/settings.json`** — I confirmed read-only that all four `PreToolUse` hooks
  (`gate_lead_write_scope.py`, `gate_spawn_needs_item.py`, `gate_commit_evidence.py`,
  `gate_todo_items.py`) plus the `agent:` lead binding live there. Under `--restricted` that file is
  **not read**, so **none of the gates run**: no lead-write-scope guard, no spawn-needs-item guard,
  no commit-evidence guard, no todo-item guard. The mode removes Bash and code-execution (which
  shrinks the attack surface the gates guard), but the **Write/Edit** tools it keeps are exactly
  what `gate_lead_write_scope` protects `project_memory/` canonical state and `.claude/` from, and
  those writes would now go **ungated** (confined only to the working dir). This is the same
  "the checker isn't in the loop" failure family as the CLAUDE.md note that a killed hook reads as
  "carry on" — except here the hooks are never registered at all. It is a **new, genuinely-changed
  threat surface**, not a hole in a gate.
- **Recommendation**: **adopt (document + decide)** — add a line to the CC-floor/install note (the
  still-open 2026-08-01 item 3) stating that **the harness gates are void under `--restricted` /
  `CLAUDE_CODE_RESTRICTED=1`** because project settings are ignored, and record the maintainer's
  decision: either (a) this repo is never run restricted (state it), or (b) the reduced tool set
  under `--restricted` is judged an acceptable substitute for the gates (name what still constrains
  a Write/Edit to canonical state in that mode). This is a threat-model note, not a code change.
  ~30 min. · **Status**: NEW

### 2. **Claude Code's own permission matcher got three command-line-parsing hardening fixes this week (2.1.243/246) — the same class the harness's H62–H70 / `_harness.command_line` work fights; mine them for gate test-vectors**
- **Source**: changelog https://code.claude.com/docs/en/changelog · seen 2026-08-28 —
  - 2.1.243: *"Fixed hook `if` conditions like `Bash(cat *)` firing on unrelated Bash commands when
    the command contained `$()` or backtick command substitution followed by more arguments"*
  - 2.1.246: *"Added a startup warning for Bash allow rules with a wildcard before the subcommand
    (e.g. `Bash(git * main)`), since they also match options inserted before the subcommand"*
  - 2.1.246: *"Fixed Bash permission checks to always require approval for malformed commands with a
    dangling `&&` or `||` operator"*
- **What it is**: Three independent fixes to how CC decides whether a shell command matches a
  permission rule — command-substitution confusing the matcher, a wildcard matching options it
  wasn't meant to, and a malformed operator slipping past.
- **Why it helps this repo**: This is **convergent, official evidence** that the harness's central
  design bet is real: a command line must be judged the way a shell reads it, not by string-match.
  `gate_commit_evidence._moves_the_tree_first` + `_harness.command_line` already reason about
  command substitution (TSK-0019) and the bare-CR / operator-parsing class (TSK-0083/0084,
  BUG-0063–0066, H62–H70). CC's `$()`/backtick fix is the **exact bug** the gate's substitution
  handling closes; CC's "wildcard before subcommand also matches inserted options" warning is the
  **exact evasion** `gate_lead_write_scope`'s Bash-line handling must survive; the dangling-operator
  fix is the malformed-line family the bare-CR work covers. **Each is a concrete test-vector**: run
  it against the gates in a throwaway clone outside the repo and confirm the gate already refuses
  (or record a measured hole in `docs/POST_V2_WISHLIST.md` with the chain if it doesn't).
- **Recommendation**: **adopt (evaluate)** — reproduce the three CC-fixed lines as gate inputs
  (`git * main`-style rule interplay only applies if the kits ship such a rule — grep confirms the
  kit `deny:`/`allow:` rules first), verify the gates' behaviour, and turn any that pass into a
  named regression test (a fix-shaped test per house rules). ~1.5–2 h. · **Status**: NEW

### 4. **Subagent first-call model 404 now silently falls back to the session's model chain (2.1.247) — a new silent-model-substitution vector that lands on the still-open per-role `model:` pinning item**
- **Source**: changelog https://code.claude.com/docs/en/changelog — 2.1.247 (Aug 26): *"Fixed
  sub-agents dying on a first-call model 404: they now use the session's fallback model chain, and
  the error returned to the parent includes the error type, status, request id, and model"* · seen
  2026-08-28
- **What it is**: Before, a subagent whose pinned model id 404'd on its first call died; now it
  silently continues on the session's fallback chain (the parent still gets an error object).
- **Why it helps this repo**: The kits tier every role by `model:` frontmatter. If a role ever pins
  a model id that 404s (a typo, a retired id, a provider that doesn't carry it), that role now
  **rides the session fallback tier instead of failing loudly** — a specialist meant for `worker`
  could silently run on the lead's tier, the same wrong-tier outcome last week's item 2 flagged when
  the "default teammate model" setting was removed. It **reinforces the recommendation there**: a
  structural test asserting every spawnable role `.md` carries a `model:` line is necessary but no
  longer sufficient — the id must also be a **live** one. Cheap add: assert each `model:` value is a
  known alias/id from `model_tiers.yaml`, not just present.
- **Recommendation**: **watch / reinforces 2026-08-21 item 2** — when that per-role `model:` test is
  built, have it also check the value resolves against the kit's tier table, so a dead id can't hide
  behind the new silent fallback. ~adds ~20 min to that item. · **Status**: NEW

### 5. **Hooks: a malformed-JSON stdout object is now reported as a hook error instead of silently read as plain text (2.1.248) — same "hook error = passthrough" family the gates must never hit**
- **Source**: changelog https://code.claude.com/docs/en/changelog — 2.1.248 (Aug 27): *"Fixed hooks
  silently treating a stdout `{…}` object that isn't valid JSON as plain text; it's now reported as
  a hook error with the parse message"* · and *"Fixed background sessions waiting silently when a
  `PermissionRequest` or `PreToolUse` hook prints an invalid answer: the `claude agents` row now
  names the hook and the schema error"* · seen 2026-08-28
- **What it is**: CC previously mis-read a not-quite-JSON `{…}` decision as plain text; now it's a
  hook error surfaced with the parse message (and background rows name the offending hook).
- **Why it helps this repo**: The four gates emit their allow/deny decision as JSON on stdout. Per
  the CLAUDE.md note, a **hook error is read by the provider as "carry on" — a passthrough** (the
  same reasoning behind the `Deadline`/`_the_budget_is_spent` timeout design and H36). This change
  means any gate that ever emits **subtly malformed JSON** flips from "treated as plain text"
  (previously non-deterministic) to "hook error → passthrough" — a cleaner failure, but still a
  **fail-open** one. Worth a read-only confirmation that every gate's decision path (including the
  budget-exceeded and deadline branches) emits strictly valid JSON, so the gate never fails open on
  a formatting slip. The improved diagnostics (row names the hook + schema error) also make a
  misfiring gate easier to spot.
- **Recommendation**: **watch (confirm)** — a maintainer pass over the gates' stdout emitters to
  confirm strict-JSON on every branch; no change if they already do. ~20 min. · **Status**: NEW
